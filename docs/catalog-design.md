# 番剧索引：从「字典」到「目录」

## 0. 你提的问题，换个说法就清楚了

现在这个 App 是一本**只有词条、没有目录**的字典：你必须先知道番名，才能在 17 个源里搜；
搜到了只有「标题 + 链接」，没有封面、简介、评分、放送时间、集数。

而用户真实的使用路径通常是反的：

- 「这季有什么新番？」——不需要知道名字
- 「周三有什么更新？」——按时间
- 「类似《芙莉莲》的还有啥」——按标签
- 「我上次看到第 8 集那个」——按进度

这三类需求都要求**索引**（catalog），而不是搜索。

## 1. 关键判断：索引和片源是两层，必须解耦

```
        ┌─────────────────────────────────────────┐
        │  索引层（元数据）：番剧是什么             │
        │  标题/别名/封面/简介/放送日/集数/评分/标签 │
        │  来源：Bangumi / AniList / TMDB           │
        └──────────────────┬──────────────────────┘
                           │  映射（标题匹配 + 缓存）
        ┌──────────────────▼──────────────────────┐
        │  片源层（规则）：在哪能看                 │
        │  某站的条目 / 线路 / 剧集 / 播放页        │
        │  来源：17 条规则                          │
        └─────────────────────────────────────────┘
```

**为什么要解耦**：

1. 规则平均 57 天死一半，但"这季有哪些番"不随规则变化——索引比片源稳定得多；
2. 一个番在索引里是唯一实体，在 17 个源里可能有 0~17 个条目，必须有个地方记录"这个番在哪些源能看"；
3. 规则全挂的时候，索引还能撑起「浏览 + 追番 + 详情」，产品不至于变白板。

## 2. 数据源选型

| 源 | 能提供 | 限制 | 定位 |
| --- | --- | --- | --- |
| **Bangumi**（api.bgm.tv v0） | 中文名/日文名、放送时间表、评分、标签、简介、关联作品、角色 | 需自设 User-Agent；限流；社区维护，字段偶有缺失 | **主源**（中文场景最贴） |
| AniList GraphQL | 英文/罗马音、季度番表、trending、评分 | 90 req/min（当前降级 30），有 burst 限制 | 备源 + 别名补充 |
| TMDB | 海报、背景图、剧照 | 需 API Key；动漫条目质量一般 | 只补图 |
| 规则站分类页 | 站点自己的"新番/排行" | 结构随时变、各不相同 | **不用**（不稳定） |

结论：**Bangumi 做主干，AniList 补别名，TMDB 只补图**。不要试图从规则站抓索引——那等于把不稳定因素再放大 17 倍。

## 3. 数据模型（SQLite / Room）

```sql
-- 番剧本体
subject(
  id            INTEGER PRIMARY KEY,
  bgm_id        INTEGER UNIQUE,
  anilist_id    INTEGER,
  title_cn      TEXT,
  title_jp      TEXT,
  title_en      TEXT,
  cover_url     TEXT,
  summary       TEXT,
  air_date      TEXT,        -- yyyy-MM-dd
  total_eps     INTEGER,
  score         REAL,
  season        TEXT,        -- 2026Q4
  status        TEXT         -- 连载/完结
)

-- 别名：映射的关键资产
alias(subject_id, name, lang, source)   -- 中文/日文/英文/罗马音/俗称

-- 周时间表
calendar(subject_id, weekday, air_time)

-- 索引 ↔ 源条目的映射缓存（最重要的表）
source_entry(
  subject_id, rule_name,
  entry_name, entry_url,
  confidence    REAL,       -- 0~1
  verified_at   INTEGER     -- 上次校验时间
)

-- 观看记录
watch(subject_id, rule_name, entry_url, episode_index, position_ms, updated_at)

-- 人工纠正（用户说"搜错了，应该是这个"）
mapping_feedback(subject_id, rule_name, chosen_title, created_at)
```

## 4. 索引怎么建

**不要一次拉全量**（Bangumi 历史条目几万条，首屏用不上）。

- **P0**：只拉「当季 + 下季 + 本周时间表」——约 200~400 部，一次请求几秒，可离线缓存；
- **增量**：每日拉一次 `calendar`（本周更新）+ 每周拉一次新番表；
- **按需补**：搜索/详情里遇到索引没有的番，实时查 Bangumi 单条并入库；
- **体检**：`source_entry` 超过 7 天的，后台抽样重新校验 URL。

体积估算：一季 300 条 × 2KB ≈ 0.6 MB，SQLite 完全无压力。

## 5. 映射：这件事真正难的地方

「从索引点进某番 → 在 17 个源里找到它」不是一次搜索就行，要解决**标题不一致**：

| 问题 | 例子 | 处理 |
| --- | --- | --- |
| 季数 | 「葬送的芙莉莲」vs「葬送的芙莉莲 第二季」 | 归一化时提取季数，**必须严格匹配**，否则第 2 季跳到第 1 季 |
| 繁简/全半角 | 「間諜過家家」/「间谍过家家」 | 统一转简体 + 全半角折叠 |
| 副标题 | 「药屋少女的呢喃 第二季」vs「药屋少女的呢喃」 | 去掉副标题再比一次 |
| 日文/罗马音 | 「Sousou no Frieren」 | 用别名表做二次搜索 |
| 俗称 | 「芙莉莲」 | 别名表 + 用户纠正 |

匹配流程：

```
1. 归一化（季数、繁简、标点、括号、全半角）
2. 用 中文名 → 日文名 → 别名 依次去每个源搜（并发，top 5）
3. 对候选打分：完全相等 1.0 / 包含 0.8 / 编辑距离相似度 / 季数一致加分 / 季数不一致直接否决
4. 置信度 > 0.9 自动采用；0.6~0.9 让用户点选；< 0.6 标记"该源暂无"
5. 采用后写 source_entry 缓存；用户手动选择的写 mapping_feedback，下次优先
```

**必须做季数校验**：这是用户最容易感知的错误（"点第二季放第一季"），一次就毁掉信任。

## 6. UI 上的入口

| 页面 | 内容 | 数据来源 |
| --- | --- | --- |
| 首页「本季新番」 | 按热度/评分排序的当季番 | 索引（离线可用） |
| 首页「时间表」 | 周一~周日，今天高亮 | calendar |
| 首页「继续观看」 | 上次看到第几集 | watch 表 |
| 搜索 | 先查本地索引（即时联想），再并发规则兜底 | 索引 + 规则 |
| 详情页 | 封面/简介/评分/标签/关联；「观看」展开各源条目 | 索引 + source_entry |
| 分类浏览 | 标签、年份、季度 | 索引 |

搜索的体验会明显变化：**输入两个字就出候选**（本地索引全文/前缀搜索），不用等 17 个规则源返回；点进详情后再按需去源里取线路。

## 7. 和现有代码的关系

新增一个 `core:catalog`（纯 JVM，可测）：

```
core/catalog/
  model/      Subject / Alias / SourceEntry
  bgm/        Bangumi v0 client（含 UA、限流退避）
  match/      标题归一化 + 相似度 + 季数校验（纯函数，重点单测）
  index/      索引仓库接口（内存实现 + Room 实现）
app/
  Room 实体与 DAO
```

规则层完全不用改：映射层只是在需要"这个番在某个源里叫什么"时调用现有的 `RuleEngine.search`。

## 8. 分阶段

| 阶段 | 内容 | 工作量 |
| --- | --- | --- |
| **P0** | 首页「本季新番 + 时间表」（Bangumi 拉取 + 缓存）；点进去复用现有搜索；详情页展示索引信息 | 2~3 天 |
| **P1** | 本地索引 + 别名表 + 匹配算法 + `source_entry` 缓存；搜索改为"索引优先 + 规则兜底" | 3~5 天 |
| **P2** | 追番 / 继续观看（watch 表 + 进度回填） | 2 天 |
| **P3** | 标签/排行浏览、多语言标题、手动纠正入口 | 3 天 |

P0 就能解决你问的"目录"问题：**用户不用知道番名，也能看到这季有什么、今天更新什么**。

## 9. 风险

- **Bangumi 限流/需要 UA**：必须有缓存和退避，不能每次进首页都打接口；镜像可选。
- **索引里的番没有任何源收录**：UI 要明确表达"暂无片源"，而不是让用户点进空列表。
- **季数匹配错误**：比"搜不到"更伤——必须硬校验。
- **映射缓存过期**：站点换域名/改结构后 `entry_url` 失效，需要定期抽检并清理。
- **法律边界**：索引是元数据（番名、放送日、评分这类事实性信息），风险远低于片源；但也别把简介全文、剧集列表当成自己的内容大量分发。

## 10. 结论

你要的"目录"不是再写 17 条规则，而是**补两层东西**：

1. **元数据索引**（从 Bangumi 同步，离线可用）——解决"有什么番"；
2. **映射层**（标题归一化 + 匹配 + 缓存）——解决"这个番在哪个源里叫什么"。

这两层做完，App 的形态会从「搜索器」变成「番剧客户端」：没网也能翻目录、规则全挂也能追番，而这恰好是当前架构最脆弱的地方。
